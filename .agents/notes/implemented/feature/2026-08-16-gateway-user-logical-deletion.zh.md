# Agent Note: Gateway 用户逻辑删除

Status: implemented

[English](2026-08-16-gateway-user-logical-deletion.md) | 中文

## 问题

管理端用户页面可以创建、禁用和重置账号，但不能移除账号。物理删除不安全，因为项目、对话、用量、内容元数据和审计事件仍然引用用户。仅把账号设为禁用也会留下会话、项目成员关系、运行时凭据和模型 intake 凭据，除非另外明确撤销这些资源。

## 决策

`DELETE /admin/api/users/:id` 执行逻辑删除。Gateway 先串行化并停止该用户的运行时，再把账号标记为禁用并写入 `users.deleted_at`，撤销认证会话，清除运行时和 intake 凭据，移除项目成员关系、用户模型授权和用户专属额度，并写入 `admin.users.delete` 审计事件。已删除行会从活跃计数、列表、用户名查询、认证、公共 ID 解析、项目授权、模型访问和 intake-token 查询中排除。home 目录、对话、内容元数据、模型用量、用量告警和审计历史继续保留，用于报告与恢复；企业范围内的用户名继续保留。

当前登录管理员不能删除自己。删除一个活跃管理员如果会导致没有其他活跃管理员则拒绝；禁用和降权也遵守同一不变量。重复删除按不存在处理，因为已删除用户不会出现在正常管理视图中。PostgreSQL 登录在创建会话前重新检查并锁定活跃用户和成员关系，因此并发删除不会在撤销后新建会话。已有会话在账号标记删除后也会验证失败。

SQLite schema 版本 5 为既有数据库加入 `users.deleted_at`。PostgreSQL migration 006 加入时间戳和活跃账号查询索引。SQLite 导入在源记录存在时把删除时间带入 PostgreSQL，同时保留历史行的企业范围与外键有效性。

## 后果

管理员可以撤销账号，而不破坏审计、用量、协作或对话历史。已删除账号不能登录、重新启动运行时、获得新的模型凭据或加入项目。恢复必须走未来明确的操作，而不是静默复用用户名；保留的 home 目录仍需要单独的保留策略。

## 曾考虑的替代方案

**物理删除用户并级联所有引用。** 否决，因为会销毁审计和用量归属、删除对话历史，并削弱持久外键保证。

**只把账号标记为禁用。** 否决，因为会话、成员关系、运行时凭据、模型授权和 intake token 仍会被配置，账号也可能继续出现在某些流程中。

**删除后允许用户名复用。** 否决，因为旧审计、对话和文件系统记录会在两个身份之间变得含义不明。

## 验证

Gateway 测试覆盖逻辑删除、历史保留、会话撤销、成员关系与凭据移除、实例停止、用户隐藏、最后管理员拒绝和认证拒绝。Admin API 测试覆盖 DELETE 响应、审计路径、列表过滤和禁止自删。Admin UI 测试覆盖确认弹窗与 DELETE 请求。配置 `HGW_TEST_DATABASE_URL` 时，PostgreSQL 集成测试覆盖 migration 006 与活跃行登录检查。
