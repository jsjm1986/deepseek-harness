# Agent Note: Project collaborative conversations

Status: implemented

English | [中文](2026-08-15-project-collaborative-conversations.zh.md)

## Problem

Gateway authentication and runtime allocation originally treated one signed-in user as the sole owner of every Harness process and conversation. Project membership granted filesystem access, but each member still entered a separate runtime with separate session persistence, so a team could not continue the same Agent conversation, inspect its shared history, or answer a pending approval or question together. Reusing one process without request-bound identity would be worse: one connection could inherit another user's authority, private conversations could leak through listing or child sessions, and simultaneous human responses could both reach the Agent.

## Decision

The Gateway allocates one runtime per user for personal scope and one shared runtime per project. An authenticated account selects its active scope through the Gateway, which proxies the browser to the corresponding runtime. Every proxied HTTP and WebSocket operation carries a short-lived Ed25519-signed principal containing the organization, user, selected scope, runtime identity, and runtime generation. `dsh-gateway-runtime` verifies that assertion inside the target process and exposes it only through request-local storage; a private loopback credential supplies the runtime bearer token and verification key without placing either secret in browser-visible configuration.

Authorization freshness is split by resource type. Root-conversation authorization and readable-session filtering query the current PostgreSQL organization role and project membership on every check, so membership removal, mode demotion, or administrator demotion applies to the next such operation. Host operations without a Session ACL use the mode captured in the signed principal; an earlier mode can remain usable only until that principal expires. The shipped Gateway default is a 30-second lifetime, every proxied HTTP request receives a new principal, and long-lived Host and Typert streams close at `expiresAt` so reconnect obtains current authority. Project-scoped Typert Remote calls are fail-closed: `goals/*` requires conversation write access, `messageFeedback/list` requires read access, `messageFeedback/put` and `messageFeedback/delete` require write access, and every unclassified or process-wide Remote is denied.

Ordinary project membership has `ro` or `rw` access. Organization administrators have implicit `rw` authority over every active project without a project-membership row. A root project conversation is either `project`, readable by every current member, or `private`, readable only by its creator and current administrators. Descendant sessions inherit the root project, creator, and visibility; they cannot define a weaker ACL. The Gateway resolves every read, write, manage, approval, and batch-list decision through the root row. A creator with `rw` membership or an administrator can change visibility, and a project-visible conversation cannot become private after another user contributes. Removing a member who still owns a private project conversation is rejected until that conversation is shared or otherwise removed.

Project identity carries an explicit `origin` and `owner`: administrator-origin projects register an existing host directory, while user-origin projects allocate an empty directory under `HGW_USER_PROJECTS_ROOT`. Both origins use one workspace, one shared runtime, one membership table, and one conversation model; the Admin API exposes one list with an origin filter and owner/creator metadata. A user owner receives `rw` membership and can invite active users with `ro` or `rw` access. Invitations are visible to their sender, recipient, project owner, and administrators; acceptance is transactional, expires are persisted, and the owner cannot be removed or demoted below `rw`. SQLite-to-PostgreSQL import derives stable invitation UUIDs from the organization and legacy invitation id, so pending invitations survive a repeatable cutover.

The administrator-only `danger-full-access` preset is available in every personal and project scope only after the request principal proves an administrator role. The `/permission` command and the new-session default path share the same authorization check, so a regular member cannot obtain the preset through settings. In a shared project session, permission events are session-global: an administrator's selection changes the in-app preset seen by all participants until another authorized selection. The project systemd unit remains path-confined, so this preset does not grant host access outside the project directory.

Collaboration is a capability seam: `dsh-collaboration` defines request-captured authority, `dsh-collaboration-gateway` obtains authoritative ACL decisions from authenticated internal Gateway endpoints, and Host/session Consumers enforce them. Host listing and search filter unreadable session ids; open, prompt, resume, fork, delete, export, stream, approval, and question operations authorize before observing or mutating session state. `ro` membership is enforced at the Host even if the browser UI is bypassed. Approval and question responses use a PostgreSQL uniqueness key over organization, interaction kind, and interaction id, so exactly one participant commits the shared response.

Project runtimes replace the local JSONL provider with `dsh-session-persistence-gateway`. It preserves the standard [`SessionPersistence`](../architecture/2026-06-14-session-persistence.md) coordinator semantics while storing headers and complete events through the private Gateway API in the PostgreSQL conversation repository introduced by the [JSONB baseline](../architecture/2026-08-14-postgresql-jsonb-gateway-baseline.md). The write API and provider response decoder admit only the event fields `type`, `seq`, `time`, `data`, `surfaceOp`, `sourceEventSeqs`, and `ignorable`; message events require a valid append or exact replace operation, while log-only events reject surface metadata. The provider retains only the coordinator's explicit pre-react-loop `steering/message` read exception. Root creation records the authenticated creator and requested visibility; child registration copies the locked root ACL. Idempotent append batches preserve contiguous event sequence, crash repair, and retries. Personal runtimes retain their configured local persistence and the [project-grouped session directory](../architecture/2026-07-24-project-session-directories.md) behavior.

Authenticated project participant metadata is attached to each admitted human message and stored in the ordinary `user/message` source. `dsh-collaboration-context` inserts a durable, model-visible metadata notice immediately before that message after the `agent/pre-step` waterfall delegates, so the model can distinguish contributors and replay reconstructs the same attribution. PostgreSQL projects participants and contribution counts from committed events; later account or membership edits do not rewrite historical attribution.

`dsh-client-ui-collaboration` owns the browser scope selector, new-root visibility choice, conversation visibility/creator/participant menu, and the complete read-only composer replacement for `ro` members. It uses existing Client slots and the `sessions/prepare-create` waterfall instead of changing the conversation shell. New Session runs that waterfall before considering a blank candidate, then `sessions/confirm-blank-reuse` asks the plugin to revalidate the candidate's root visibility through the Gateway; only an exact visibility match is reusable. Scope changes reload the page because personal and project scopes target different Host processes. Shared project runtimes expose Host settings as read-only: settings consumers do not attempt mutations, and the welcome notice keeps its acknowledgement only in the current Client process so a full page load presents it again. Browser controls are affordances; signed principals, Host authorization, internal APIs, and PostgreSQL transactions remain authoritative.

Linux systemd units mask the users root, project-runtime root, and every configured project-data root with read-only temporary filesystems before re-binding only the current runtime home, `$DSH_HOME`, and authorized project paths. `ProtectHome=tmpfs` and a capability set without `CAP_SYS_ADMIN` prevent instances from recovering the hidden host tree through home directories or mount operations. Administrator-origin projects reject paths that overlap users, runtime data, the Gateway directory, or another project, and every production project path must be a strict descendant of one non-overlapping `HGW_PROJECT_PATH_ROOTS` entry. User-origin projects allocate below `HGW_USER_PROJECTS_ROOT`, which must be provisioned with `HGW_PROJECT_RUNTIME_USER` group inheritance (for example a root-owned setgid `2770` directory or an equivalent default ACL) so newly created folders are readable and writable by their project unit. Shared units cannot run as root. Gateway startup serializes node-local port allocation with a PostgreSQL advisory transaction lock and creates missing active project runtime rows from `HGW_INSTANCE_PORT_BASE`.

Project model usage, intake credentials, quotas, and threshold alerts are keyed to the shared project runtime rather than to whichever member sent one prompt. The admin project detail view requires an explicit choice between inheriting the ordinary-member quota and using a project-specific token-plus-company-cost quota, and displays the project's natural-month usage with the same accounting primitives as the global Usage view.

Project deletion first stops the shared runtime while retaining its serialized instance-operation slot, then deletes the PostgreSQL project. Foreign-key cascades remove its runtime row, memberships and mounts, conversation trees and events, participant and interaction rows, model usage, quota and alert rows, intake token, and content-file metadata. The project directory itself is never deleted.

The repository production entry, `pnpm run build:production`, builds the Harness libraries and Web application, both required out-of-tree plugins, and the Admin SPA; typechecks the Gateway; and rejects a release tree missing any required CLI, Web, Admin, plugin, administrator overlay, or collaboration migration payload.

Gateway tests cover systemd masking and rebinding, project-root validation, runtime write-envelope rejection, configured port parsing, and administrator access to an unmaterialized private root. Host/API Proxy tests cover denial across session operations, readable-list filtering, participant propagation, root creation visibility, and atomic approval/question claims. Real PostgreSQL tests cover migrations through 5, full JSON event round trips, repeatable SQLite import including project invitations, shared runtime allocation from a configured empty-node port base, creator/private visibility, current-role administrator override without project membership, child inheritance, contribution projection, membership-removal protection, interaction races, project credentials, project usage, and explicit project quota modes. Gateway and permission tests cover origin-filtered Admin views, user-owned project and invitation lifecycle, administrator `fullAccess` in personal and project scopes, and rejection of an administrator-only new-session default. A keyless assembled Web browser scenario covers project scope, visibility controls, participant display, mismatched-blank rejection and matching-blank reuse, the `ro` experience, and process-local welcome acknowledgement through the shipped Client composition. The production build entry verifies the complete runtime payload after every component build.

## Alternatives considered

**Copy a conversation into each member's personal runtime.** Rejected because copies diverge immediately, cannot share one pending interaction, duplicate model cost, and lose one append-only event order.

**Keep one project runtime but store the active user in a process-global variable.** Rejected because concurrent HTTP, WebSocket, stream, and background operations would race and could apply one participant's authority or attribution to another participant's request.

**Enforce collaboration only in the Web UI.** Rejected because direct RPC calls, stale clients, reconnects, and non-visual Consumers would bypass it. The UI explains and prevents unavailable actions, while Host and Gateway authorization decide them.

**Give every descendant session an independent visibility.** Rejected because a private child under a shared root or a shared child under a private root makes listing, fork, resume, and transcript authorization ambiguous. One root ACL keeps the conversation tree atomic.

**Accept every approval or question response and let event order choose.** Rejected because two users can race through different connections before either observes the other's event. The database claim is the commit point and later responses receive an explicit already-answered result.

**Write shared project conversations to a project-local JSONL directory.** Rejected because a shared runtime needs centralized authorization, concurrency, queryable participants, atomic interaction claims, and coordinated recovery. The existing persistence interface already permits a PostgreSQL provider without changing Session semantics.

**Share one personal conversation with a direct link.** Rejected because a conversation share does not define the workspace folder, runtime identity, inherited child-session ACL, invitation lifecycle, or project-level usage and governance. Collaboration is attached to a project that owns those resources; a conversation can still be marked project-visible or creator-private inside it.

**Maintain separate administrator-workspace and user-workspace data models.** Rejected because both origins need the same folder/runtime/membership/conversation invariants. One project table with explicit origin and owner metadata keeps the Admin view unified while preserving who provisioned the workspace.

## Consequences

Project members collaborate in one durable conversation tree with explicit visibility, authenticated participant attribution, shared approvals/questions, shared model accounting, and one runtime over the project filesystem. Private project conversations remain creator-only for ordinary members, while current organization administrators retain full access. Session ACL checks observe project-membership and administrator-role changes immediately; operations that rely only on a captured project scope are bounded by the principal lifetime rather than a runtime restart.

The design adds a hard runtime dependency on the loopback Gateway and PostgreSQL for project scope; there is no offline ACL cache or local project-session fallback. Scope switching reloads the browser, long-lived connections must reconnect before principal expiry, participant identity is historical snapshot data, and project-visible conversations cannot be made private after another contributor participates. Permission selection is session-global in a shared runtime, while filesystem confinement remains project-scoped. Managed-folder provisioning requires a host group/default ACL. Personal conversations and their local persistence remain separate from project collaboration.
