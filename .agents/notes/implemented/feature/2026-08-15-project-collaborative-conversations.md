# Agent Note: Project collaborative conversations

Status: implemented

English | [中文](2026-08-15-project-collaborative-conversations.zh.md)

## Problem

Gateway authentication and runtime allocation originally treated one signed-in user as the sole owner of every Harness process and conversation. Project membership granted filesystem access, but each member still entered a separate runtime with separate session persistence, so a team could not continue the same Agent conversation, inspect its shared history, or answer a pending approval or question together. Reusing one process without request-bound identity would be worse: one connection could inherit another user's authority, private conversations could leak through listing or child sessions, and simultaneous human responses could both reach the Agent.

## Decision

The Gateway allocates one runtime per user for personal scope and one shared runtime per project. An authenticated account selects its active scope through the Gateway, which proxies the browser to the corresponding runtime. Every proxied HTTP and WebSocket operation carries a short-lived Ed25519-signed principal containing the organization, user, selected scope, runtime identity, and runtime generation. `dsh-gateway-runtime` verifies that assertion inside the target process and exposes it only through request-local storage; a private loopback credential supplies the runtime bearer token and verification key without placing either secret in browser-visible configuration.

Authorization freshness is split by resource type. Root-conversation authorization and readable-session filtering query current PostgreSQL membership on every check, so membership removal or demotion applies to the next such operation. Host operations without a Session ACL use the mode captured in the signed principal; an earlier mode can remain usable only until that principal expires. The shipped Gateway default is a 30-second lifetime, every proxied HTTP request receives a new principal, and long-lived Host and Typert streams close at `expiresAt` so reconnect obtains current membership. Project-scoped Typert Remote calls are fail-closed: `goals/*` requires conversation write access, `messageFeedback/list` requires read access, `messageFeedback/put` and `messageFeedback/delete` require write access, and every unclassified or process-wide Remote is denied.

Project membership has `ro` or `rw` access. A root project conversation is either `project`, readable by every current member, or `private`, readable only by its creator. Descendant sessions inherit the root project, creator, and visibility; they cannot define a weaker ACL. The Gateway resolves every read, write, manage, approval, and batch-list decision through the root row. Only the creator with `rw` membership can change visibility, and a project-visible conversation cannot become private after another user contributes. Removing a member who still owns a private project conversation is rejected until that conversation is shared or otherwise removed.

Collaboration is a capability seam: `dsh-collaboration` defines request-captured authority, `dsh-collaboration-gateway` obtains authoritative ACL decisions from authenticated internal Gateway endpoints, and Host/session Consumers enforce them. Host listing and search filter unreadable session ids; open, prompt, resume, fork, delete, export, stream, approval, and question operations authorize before observing or mutating session state. `ro` membership is enforced at the Host even if the browser UI is bypassed. Approval and question responses use a PostgreSQL uniqueness key over organization, interaction kind, and interaction id, so exactly one participant commits the shared response.

Project runtimes replace the local JSONL provider with `dsh-session-persistence-gateway`. It preserves the standard [`SessionPersistence`](../architecture/2026-06-14-session-persistence.md) coordinator semantics while storing headers and complete events through the private Gateway API in the PostgreSQL conversation repository introduced by the [JSONB baseline](../architecture/2026-08-14-postgresql-jsonb-gateway-baseline.md). The write API and provider response decoder admit only the event fields `type`, `seq`, `time`, `data`, `surfaceOp`, `sourceEventSeqs`, and `ignorable`; message events require a valid append or exact replace operation, while log-only events reject surface metadata. The provider retains only the coordinator's explicit pre-react-loop `steering/message` read exception. Root creation records the authenticated creator and requested visibility; child registration copies the locked root ACL. Idempotent append batches preserve contiguous event sequence, crash repair, and retries. Personal runtimes retain their configured local persistence and the [project-grouped session directory](../architecture/2026-07-24-project-session-directories.md) behavior.

Authenticated project participant metadata is attached to each admitted human message and stored in the ordinary `user/message` source. `dsh-collaboration-context` inserts a durable, model-visible metadata notice immediately before that message after the `agent/pre-step` waterfall delegates, so the model can distinguish contributors and replay reconstructs the same attribution. PostgreSQL projects participants and contribution counts from committed events; later account or membership edits do not rewrite historical attribution.

`dsh-client-ui-collaboration` owns the browser scope selector, new-root visibility choice, conversation visibility/creator/participant menu, and the complete read-only composer replacement for `ro` members. It uses existing Client slots and the `sessions/prepare-create` waterfall instead of changing the conversation shell. Scope changes reload the page because personal and project scopes target different Host processes. Browser controls are affordances; signed principals, Host authorization, internal APIs, and PostgreSQL transactions remain authoritative.

Linux systemd units mask the users root, project-runtime root, and every configured project-data root with read-only temporary filesystems before re-binding only the current runtime home, `$DSH_HOME`, and authorized project paths. `ProtectHome=tmpfs` and a capability set without `CAP_SYS_ADMIN` prevent instances from recovering the hidden host tree through home directories or mount operations. Project creation rejects paths that overlap users, runtime data, the Gateway directory, or another project, and requires each production project path to be a strict descendant of one non-overlapping `HGW_PROJECT_PATH_ROOTS` entry. Shared units cannot run as root. Gateway startup serializes node-local port allocation with a PostgreSQL advisory transaction lock and creates missing active project runtime rows from `HGW_INSTANCE_PORT_BASE`.

Project model usage, intake credentials, quotas, and threshold alerts are keyed to the shared project runtime rather than to whichever member sent one prompt. The admin project detail view requires an explicit choice between inheriting the ordinary-member quota and using a project-specific token-plus-company-cost quota, and displays the project's natural-month usage with the same accounting primitives as the global Usage view.

Project deletion first stops the shared runtime while retaining its serialized instance-operation slot, then deletes the PostgreSQL project. Foreign-key cascades remove its runtime row, memberships and mounts, conversation trees and events, participant and interaction rows, model usage, quota and alert rows, intake token, and content-file metadata. The project directory itself is never deleted.

## Verification

Package tests cover principal and launch-credential validation, provider disposal, strict event-response decoding, root-inherited ACLs, participant attribution and invariants, Gateway persistence behavior, Client state and component behavior, and `ro` composer replacement. Gateway tests cover systemd masking and rebinding, project-root validation, runtime write-envelope rejection, and configured port parsing. Host/API Proxy tests cover denial across session operations, readable-list filtering, participant propagation, root creation visibility, and atomic approval/question claims. Real PostgreSQL tests cover migration 3, shared runtime allocation from a configured empty-node port base, creator/private visibility, child inheritance, contribution projection, membership-removal protection, interaction races, project credentials, project usage, and explicit project quota modes. A keyless assembled Web browser scenario covers project scope, visibility controls, participant display, and the `ro` experience through the shipped client composition.

## Alternatives considered

**Copy a conversation into each member's personal runtime.** Rejected because copies diverge immediately, cannot share one pending interaction, duplicate model cost, and lose one append-only event order.

**Keep one project runtime but store the active user in a process-global variable.** Rejected because concurrent HTTP, WebSocket, stream, and background operations would race and could apply one participant's authority or attribution to another participant's request.

**Enforce collaboration only in the Web UI.** Rejected because direct RPC calls, stale clients, reconnects, and non-visual Consumers would bypass it. The UI explains and prevents unavailable actions, while Host and Gateway authorization decide them.

**Give every descendant session an independent visibility.** Rejected because a private child under a shared root or a shared child under a private root makes listing, fork, resume, and transcript authorization ambiguous. One root ACL keeps the conversation tree atomic.

**Accept every approval or question response and let event order choose.** Rejected because two users can race through different connections before either observes the other's event. The database claim is the commit point and later responses receive an explicit already-answered result.

**Write shared project conversations to a project-local JSONL directory.** Rejected because a shared runtime needs centralized authorization, concurrency, queryable participants, atomic interaction claims, and coordinated recovery. The existing persistence interface already permits a PostgreSQL provider without changing Session semantics.

## Consequences

Project members collaborate in one durable conversation tree with explicit visibility, authenticated participant attribution, shared approvals/questions, shared model accounting, and one runtime over the project filesystem. Private project conversations remain creator-only even though their process is shared. Session ACL checks observe membership changes immediately; operations that rely only on a captured project scope are bounded by the principal lifetime rather than a runtime restart.

The design adds a hard runtime dependency on the loopback Gateway and PostgreSQL for project scope; there is no offline ACL cache or local project-session fallback. Scope switching reloads the browser, long-lived connections must reconnect before principal expiry, participant identity is historical snapshot data, and project-visible conversations cannot be made private after another contributor participates. Personal conversations and their local persistence remain separate from project collaboration.
