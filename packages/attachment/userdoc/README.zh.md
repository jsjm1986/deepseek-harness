# @deepseek-ai/dsh-userdoc

[English](README.md) | 中文

用户文档服务边界。`ctx.userDocs` 把用户上传的文件按普通文件存放在主机上，随后返回携带真实绝对路径的 `UserDocRef`。这个路径正是该边界存在的意义：上传的文档可以被 agent 自己的 `read`、`grep`、`glob` 和 shell 工具直接读取，因此模型不需要学习任何单独的取回通道。

这与 [`dsh-attachment`](../attachment/README.md) 刻意相反——后者的对象是内容寻址的、私有的，且对文件工具不可见。两个边界并存：图片继续走附件路径，因为提供方需要把字节内联进请求；文档保留文件系统路径，因为 agent 会像读任何其他文件一样读它。

`resolveTarget` 是一个显式步骤，而不是藏在 `save` 里的默认行为：它净化客户端提供的文件名、在上传根目录内解析目标，并返回 `save` 将要创建的确切路径。调用方先解析、再把字节流交给 `save`，因此准入与目录包含关系在写入第一个字节之前就已决定。`save` 按实际收到的字节强制执行 `maxFileBytes`——绝不信任声明的长度——并在拒绝时不留下任何残留文件。

`mediaType` 按原样记录，从不校验、解析或据此分派。这里没有格式白名单。harness 接受用户上传的任何内容，并让 agent 判断文件是什么；服务端解析、文本抽取和缩略图生成按设计不属于该边界。

存储不是内容寻址的，因此字节完全相同的两次上传就是两个文件、两个标识符。删除其中一个不会影响另一个，这符合用户对自己目录中文件的预期。

## 模型体验

该包通过主机的提示装配消费方间接影响模型：消费方依据本服务边界提供的引用与 `maxInlineTextBytes` 阈值，要么把可解码的小文档内联为文本，要么传递其路径交由 agent 的常规文件工具读取。

#### KV 缓存影响

无；本包既不装配也不发送提供方请求。

## 已知限制与待完成工作

- **没有保留策略、配额记账或垃圾回收** —— 上传内容会一直留在用户自己的目录下，直到被删除。多用户部署需在自己的层面强制磁盘配额，因为该边界看不到共享同一卷的其他用户。
- **`list` 只遍历一个上传根目录** —— 没有搜索、没有分页、没有跨根视图，因此超大的上传历史只能整份列出，或者干脆不列。
- **读取时不做内容校验** —— 与内容寻址的附件路径不同，文档是普通文件，任何拥有文件系统访问权的主体都可能在上传后修改它，而 `bytes` 是上传时记录的长度。
